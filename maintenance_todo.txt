--- BUG (money): a purchase in ANY app on this Stripe account credits this one ---
Found 2026-08-08 from the reddit-comment-cluster (Analyzer) side, while working
out why a top-up there errored. Not yet fixed on this side. Worth doing before
Play Console, because this app is the one already taking real money.

The problem: Stripe account acct_1FHXJdBOSVZFOip0 is shared between this app and
Analyzer, and Stripe fans every `checkout.session.completed` out to EVERY enabled
endpoint on the account — not just the one belonging to the app that created the
session. Neither app tagged its sessions, so each webhook credited on any
completion it received.

Why it isn't caught by anything: both apps' schemas hang off the same shared
`auth.users` in the keeper project (ycuuxnscbxiibsnefgef), so a user id from an
Analyzer checkout resolves fine in `argument_mapper.profiles`. The wrong-app
`add_credits` SUCCEEDS silently. No error, no failed delivery, nothing to notice
— just free credits.

The two files here:
  - supabase/functions/create-checkout-session/index.ts:57-61 — sets
    client_reference_id and metadata.credits_cents, no app marker.
  - supabase/functions/stripe-webhook/index.ts:22-40 — credits on any
    checkout.session.completed, no check of who created the session.

The fix, mirroring what's already landed on the Analyzer side
(reddit-comment-cluster/reddit-proxy-worker.js, `APP_ID` const):
  1. Stamp `app: "argument_mapper"` into the session metadata on creation.
  2. In the webhook, return 200 early for any session whose metadata.app isn't
     that value. 200 rather than 400 on purpose — a sibling app's event is
     correctly delivered and correctly ignored, so reporting failure just buys
     retries and a red error rate on a healthy endpoint.
  3. Deploy the Edge Functions. Note the ordering hazard: once the webhook
     starts requiring the marker, a checkout session created BEFORE the deploy
     has no marker and would be ignored. Deploy create-checkout-session first,
     or accept the small in-flight window.
The exact string doesn't have to match anything on the Analyzer side — it only
checks for its own 'analyzer'. What matters is that this app stamps something
and checks for it.

--- PLAN (not yet built): mock the Thorough E2E tier's backend ---
2026-07-26 alignment review against /home/alex/apps/shared/testing-guidelines.md
found the biggest gap: that doc wants the "Thorough" test tier (tests/*.spec.js
minus @costly) to run against a fully mocked backend — "zero cost and zero
flakiness from real network dependencies" — and treats this as the preferred
foundation, not an optional nicety. Right now every test in this suite,
including the free ones, hits the real production Supabase project and reads/
writes real rows in the real `debates` table. That's the direct cause of the
2026-07-26 incident where a test's cleanup step deleted a real user debate
(see [[feedback_test_cleanup_by_id]] in Claude's project memory / git log
8cdf5ce) — mocking would have made that bug inert instead of destructive.
Alex asked for this scoped out before any code changes. Proposed shape:

  What gets mocked (via Playwright's page.route() intercepting requests to
  *.supabase.co):
    - Auth (/auth/v1/*) — sign-in returns a canned session object. This
      actually makes tests/auth.setup.js simpler/faster than today: inject a
      fake session directly into localStorage (matching the
      sb-<ref>-auth-token key we already inspected the shape of) instead of
      doing a real network round-trip at all.
    - The `debates` table (/rest/v1/debates, Accept-Profile: argument_mapper)
      — GET/POST/PATCH/DELETE served from an in-memory fixture, reset per
      test. This is the one that matters most: it's what node-lifecycle.spec.js
      and history.spec.js touch, and what caused the real-data-loss bug.

  What probably stays real even after this:
    - Stripe Checkout session creation (buy-credits.spec.js) — the shared doc
      explicitly sanctions "open a checkout session, verify it, close without
      paying" as an acceptable real-integration test even in Thorough, since
      it can't actually charge anything. Could still mock it for speed/
      determinism if preferred — flagging as a decision point, not a given.
    - Everything tagged @costly (new-argument-combined, messy-arguments) —
      by definition these need the real Claude/AI pipeline to be meaningful;
      mocking them would defeat the point of the test.

  Open questions to resolve before implementation:
    - Fixture data shape: hand-write a small set of representative `debates`
      rows (few nodes, many nodes, various node types/flags) so tests have
      something realistic to assert against, vs. deriving fixtures from a
      real export.
    - How to keep mocked fixtures from silently drifting out of sync with the
      real Supabase schema over time — the shared doc's own answer is
      "should be checked against production periodically too," so this
      wouldn't replace occasional real-backend runs, just make routine ones
      free and safe.
    - Whether to build this incrementally (mock `debates` first since it's
      the highest-risk one, decide on auth/Stripe after) or all at once.

--- FEATURE: User-provided API keys ---
Allow users to paste their own Anthropic API key in a settings screen. The key
would be stored in localStorage (stays on-device, never sent to our servers
except as a request header to the Edge Function). The Edge Function would use
the user-supplied key instead of the server key when one is present. This
eliminates all API cost risk for the developer and lets power users run the app
without any per-use charges. Implementation notes:
  - Add a "Settings" screen or modal with an API key input field
  - Validate the key format client-side (starts with "sk-ant-")
  - Pass it as a custom header (e.g. X-Us   er-Api-Key) to the Edge Function
  - Edge Function checks for the header and prefers it over the env-var key
  - Show a clear indicator in the UI when the user's own key is active
  - Consider only supporting Anthropic keys for now; other providers
    (OpenAI, Gemini) would require separate API request formats and
    system prompt tuning and are a larger project
