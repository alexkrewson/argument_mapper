  DELETE-ACCOUNT DESIGN — settled, don't redesign it
  A spec was floated 2026-07-31 (from another Claude conversation, written
  without the repo in front of it) proposing app_id columns on every table,
  an app_memberships table, and RLS scoped on user_id + app_id. REJECTED for
  this project, because:
    - Apps here are separated by Postgres SCHEMA, not by an app_id column.
      The spec would rebuild existing isolation across three live apps and
      leave two overlapping mechanisms in place.
    - Its RLS uses current_setting('request.app_id'), which PostgREST does not
      expose (it has request.headers / request.jwt.claims / request.method /
      request.path). As written the policy evaluates to NULL and denies
      everything.
    - app_id chosen by the client is not a security boundary in any case,
      header or where-clause. Its own fallback admits this.
    - Its steps 4-5 (service-role function, per-app delete, identity cleanup)
      are already implemented in 67b4d87.
  The one good idea in it is app_memberships replacing the hand-maintained
  OTHER_APP_TABLES probe list. Not needed after the split (no other apps in
  the project). Revisit only if a fourth app ever shares a project — and if so,
  write membership rows on FIRST USE, not signup: the shared signup trigger
  already writes a profiles row into every schema for every user, which is
  exactly why profiles is excluded from the probe. Membership-at-signup would
  reproduce that bug precisely and the identity would never be deletable.

  Also settled: when someone picks full account deletion AND has data in other
  apps, we WARN and let them proceed. We do not silently downgrade to
  data-only. Someone who clicks through two confirmations and a warning naming
  the other apps has asked for what they get.

  AFTER CLOSED TESTING — OAuth sign-in (Google / Facebook / Apple)
  [ ] Asked about 2026-07-31. Doable, free, built into Supabase Auth, but not
        before testers land — it's a new auth surface and email/password works.
        Three things to settle first:
        - Google refuses OAuth inside embedded WebViews (disallowed_useragent),
          and the APK IS a WebView. Works in the browser, fails in the app —
          same shape as the clipboard and Stripe-redirect bugs. Needs a system
          browser / Custom Tab round trip via deep link, or native sign-in.
        - Reopens the shared-identity question. One row per email is a hard
          rule in Supabase Auth, so signing up in another app with a password
          and then using "Sign in with Google" on the same address either links
          to the existing identity or errors, depending on a Supabase
          identity-linking setting. CHECK THE CURRENT DEFAULT before building.
        - Facebook needs business verification and app review. Google alone is
          the 90% answer. Apple requires Sign in with Apple if iOS ever ships
          with any third-party login.

        WEB IS EASY, and worth saying plainly because it sounded harder than it
        is: one call, supabase.auth.signInWithOAuth({ provider: 'google' }).
        Full-page redirect to Google's own screen, back to the app, supabase-js
        picks the session out of the URL. NO custom page to build; a
        /auth/callback route is optional tidiness. The work is configuration —
        Google Cloud OAuth client, paste ID/secret into Supabase, add
        Supabase's callback URL to Google's authorized redirect list. Also move
        the consent screen out of "Testing" (small user cap) before testers.

        ANDROID, two options:
          1. Browser round-trip — Custom Tab (a real browser, so Google
             accepts it) plus a deep link home, via custom scheme
             (idisagree://auth) or App Links verified against
             idisagree.trolleysolution.com. Cloudflare Pages can host the
             assetlinks file.
          2. Native account picker (Credential Manager) — bottom sheet, no
             browser, better UX.
        DO 1 FIRST. Option 2's catch: the native client binds to the app's
        SIGNING CERTIFICATE. Debug and release differ so both need
        registering, and with Play App Signing the fingerprint that matters in
        production is GOOGLE's, which you cannot know until after the first
        upload. So the native picker can't be fully verified until the app is
        on a Play track — the same wall as Play Billing, and likely the same
        emulator problem (a real Google account generally wants a Play-Store
        image; the AVD is google_apis). The browser round-trip has none of
        those dependencies and shares one code path with web.

        SET UP AFTER THE SUPABASE SPLIT, NOT BEFORE. The OAuth client is bound
        to a project — the callback URL contains the project ref — so doing it
        on the keeper means doing it twice.

        THE PATTERN WORTH NOTICING: Play Billing and the native account picker
        are both untestable until something is uploaded. If either is wanted,
        the move is to get a build onto INTERNAL testing early — that track
        needs neither the 12 testers nor the 14 days, which are closed-track
        requirements.

--- FEATURE: User-provided API keys ---
Allow users to paste their own Anthropic API key in a settings screen. The key
would be stored in localStorage (stays on-device, never sent to our servers
except as a request header to the Edge Function). The Edge Function would use
the user-supplied key instead of the server key when one is present. This
eliminates all API cost risk for the developer and lets power users run the app
without any per-use charges. Implementation notes:
  - Add a "Settings" screen or modal with an API key input field
  - Validate the key format client-side (starts with "sk-ant-")
  - Pass it as a custom header (e.g. X-Us   er-Api-Key) to the Edge Function
  - Edge Function checks for the header and prefers it over the env-var key
  - Show a clear indicator in the UI when the user's own key is active
  - Consider only supporting Anthropic keys for now; other providers
    (OpenAI, Gemini) would require separate API request formats and
    system prompt tuning and are a larger project
